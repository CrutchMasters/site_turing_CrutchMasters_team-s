## Про проєкт

**CodeFuture** — комплексна екосистема для проведення IT-турнірів та хакатонів. Платформа об'єднує три ролі: **організатори**, **учасники** та **жюрі** — і супроводжує їх від створення турніру до оголошення переможців.

## Функціонал

Платформа побудована навколо трьох ролей: **організатор** (admin), **учасник** (user) та **жюрі** (jury). Кожна роль має свій набір можливостей та інтерфейс.

---

### 🔐 Авторизація та ролі

- Реєстрація через email з підтвердженням OTP-кодом (6 цифр на пошту)
- Вхід за логіном або email + пароль
- Скидання паролю через email-посилання
- Чотири рівні доступу: `user` → `jury` → `admin` → `superadmin`
- JWT-авторизація з підтримкою як HS256, так і ES256 (JWKS)
- Автоматичне оновлення токенів без виходу із системи

---

### 🏆 Управління турнірами (для організаторів)

- Створення турніру з повним набором параметрів:
  - назва, опис, правила (Rich Text Editor з підтримкою форматування)
  - дата та час початку/кінця турніру
  - окреме вікно реєстрації команд (від/до)
  - мінімальний та максимальний розмір команди
  - максимальна кількість команд
  - кількість раундів та їх індивідуальні налаштування
- Статуси турніру з автоматичним переходом за розкладом (APScheduler):
  - `upcoming` → `registration` → `ongoing` → `finished`
- Завантаження та редагування банера турніру (кроп, зміна через BannerEditorModal)
- Публічна сторінка турніру з вкладками «Інформація» та «Лідерборд»
- Список зареєстрованих команд з аватарами та складом
- Список членів жюрі
- Редагування всіх параметрів турніру після створення
- Видалення турніру організатором
- Налаштування кількості жюрі на одну роботу (`jury_per_submission`)

---

### 📋 Раунди

- Кожен турнір має один або кілька раундів з незалежними налаштуваннями
- Для кожного раунду задаються: назва, опис, дати початку/кінця, статус
- Критерії оцінювання для кожного раунду є **обов'язковими** — без них раунд не може бути створений
- Організатор задає довільну кількість критеріїв із назвами та вагами у відсотках (сума ваг має дорівнювати 100%)
- Ручна зміна статусу раунду організатором
- Прикріплення файлів до раунду (умови завдання, матеріали)

---

### 👥 Команди та учасники

- Створення команди з назвою та прив'язкою до міста/школи/організації
- Роль капітана: управління складом, редагування команди, розпуск
- Запрошення учасників двома способами:
  - пошук по платформі (за username)
  - надсилання email-запрошення
- Прийняття/відхилення запрошень у профілі
- Кік учасника капітаном
- Валідація при реєстрації на турнір: перевірка мін/макс складу, унікальності учасників
- Аватар команди через AvatarEditorModal (кроп зображення)
- Сторінка команди: склад, турніри, статуси

---

### 📝 Подача рішень (Submissions)

- Форма сабміту містить:
  - посилання на GitHub-репозиторій
  - посилання на YouTube-демо
  - посилання на live-версію проєкту
  - текстовий опис у Rich Text Editor
  - прикріплення файлів (підтримуються: зображення, відео, PDF, архіви, код, інші)
- Живий таймер зворотного відліку до дедлайну прямо на сторінці
- Статус сабміту: `draft` / `submitted` / `evaluated`
- Можливість оновити сабміт до закриття раунду
- Видалення окремих файлів із сабміту
- Перегляд власного сабміту після подачі
- Організатор/жюрі бачать список усіх сабмітів раунду з деталями

---

### ⚖️ Система жюрі та оцінювання

**Запрошення жюрі:**
- Надсилання запрошення через email із токеном (унікальне посилання)
- Реєстрація жюрі за посиланням з автоматичним прийняттям ролі
- Запрошення безпосередньо зареєстрованих користувачів платформи
- Перегляд і управління списком жюрі турніру

**Розподіл робіт:**
- Автоматичний розподіл: алгоритм балансує навантаження між членами жюрі — кожен отримує приблизно однакову кількість робіт
- Рандомний tie-breaking при однаковому навантаженні (захист від упередженості)
- Ручний перерозподіл усіх робіт (redistribute)
- Частковий перерозподіл: тільки нові або нерозподілені роботи (partial redistribute)
- Ручне призначення конкретної роботи конкретному журисту

**Оцінювання:**
- Панель жюрі з навігацією по призначених роботах
- Для кожної роботи: перегляд GitHub, відео-демо, опису, файлів
- Оцінка по кожному критерію (0–100) з урахуванням ваги критерію
- Текстовий коментар до кожного критерію
- Загальний бал розраховується автоматично: `Σ (score × weight / 100)` — **на сервері** за критеріями раунду (значення від клієнта ігнорується)
- Оцінку можна зберегти частково; у таблицю лідерів потрапляють лише **повні** оцінки (бал виставлено за кожен критерій)
- Статуси оцінювання: `not_evaluated` / `in_progress` / `evaluated`
- Перегляд прогресу оцінювання по раунду (скільки оцінено із загального числа)

---

### 📊 Лідерборд та аналітика

- Динамічний лідерборд турніру з місцями (🥇🥈🥉 + числові позиції); команди з однаковою сумою ділять місце (1, 1, 3)
- Розбивка балів по кожному раунду окремо; бал за раунд — середнє за повними оцінками журі, підсумок — сума за раунди
- Позначка «Попередні результати», доки не всі раунди оцінено
- **Додатковий рейтинг із поправкою на строгість суддів** (перемикач на сторінці лідерборда): офіційні місця визначаються простим середнім, а скоригований рейтинг показує, як би виглядала таблиця, якби судді були однаково суворими
- Сортування за загальним балом
- Фільтрація та відображення: назва команди, місто/школа, капітан
- Експорт результатів у CSV з усіма раундами та балами (у форматі UTF-8 BOM для Excel)

## Швидкий старт

### Вимоги
- Ubuntu 20.04+ (або будь-який Linux)
- Node.js 20+ (встановлюється через NVM)
- Python 3.12 або 3.13 (рекомендовано). На Python 3.14 для частини пакетів (`pyiceberg`, `pyroaring`) немає готових збірок, тож вони компілюються з вихідників — потрібні `build-essential` і `python3-dev` (див. нижче)
- Обліковий запис [Supabase](https://supabase.com)

### Налаштування Supabase

Перед запуском створіть проєкт у Supabase та додайте змінні оточення.

Для **frontend** створіть файл `frontend/.env.local`:
```env
NEXT_PUBLIC_SUPABASE_URL=https://ваш-проєкт.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=ваш-anon-key
NEXT_PUBLIC_API_URL=http://localhost:8000
```

Для **backend** створіть файл `backend/.env`:
```env
SUPABASE_URL=https://ваш-проєкт.supabase.co
SUPABASE_KEY=ваш-anon-key
SUPABASE_SERVICE_KEY=ваш-service-role-key
SUPABASE_JWT_SECRET=ваш-jwt-secret
```

Усі ключі беруться в Supabase: **Project Settings → API** (`anon`, `service_role`, JWT Secret).

| Змінна | Обов'язкова | Для чого |
|---|---|---|
| `SUPABASE_URL` | так | Адреса проєкту Supabase |
| `SUPABASE_SERVICE_KEY` | так | `service_role`-ключ: доступ до БД та Storage з бекенду. Без нього бекенд не підключиться до Supabase |
| `SUPABASE_KEY` | так | `anon`-ключ: вхід користувачів (`sign_in_with_password`) |
| `SUPABASE_JWT_SECRET` | рекомендовано | Перевірка підпису JWT. Без нього підпис токенів не перевіряється (у логах буде попередження) |
| `GMAIL_USER`, `GMAIL_APP_PASSWORD` | ні | Email-сповіщення через Gmail SMTP (пароль додатка). Без них листи не надсилаються |
| `SITE_URL` | ні | Адреса фронтенду для посилань у листах (за замовчуванням `http://localhost:3000`) |
| `API_URL` | ні | Публічна адреса бекенду для посилань у листах (за замовчуванням `http://localhost:8000`) |
| `FRONTEND_URL` | на проді | Адреса фронтенду для редиректів після прийняття запрошень. Задайте актуальну — значення за замовчуванням вказує на старий Vercel-деплой |
| `CORS_EXTRA_ORIGINS` | ні | Додаткові дозволені origin через кому |

> **Не комітьте `.env`** — він у `.gitignore`. Ключ `service_role` дає повний доступ до бази.

### 🖥 Встановлення Frontend

```bash
# 1. Оновлення системи
sudo apt update && sudo apt upgrade -y

# 2. Встановлення curl
sudo apt install curl

# 3. Встановлення NVM
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

# 4. Завантаження NVM у поточну сесію
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"
[ -s "$NVM_DIR/bash_completion" ] && \. "$NVM_DIR/bash_completion"

# або просто:
source ~/.bashrc

# 5. Встановлення Node.js 20
nvm install 20
nvm use 20

# 6. Перехід до директорії фронтенду (з кореня репозиторію) та встановлення залежностей
cd frontend
npm install

# 7. Запуск у режимі розробки
npm run dev
```

Фронтенд буде доступний за адресою: **http://localhost:3000**

### ⚙️ Встановлення Backend

```bash
# 1. Встановлення python3-venv, а також компілятора й заголовків Python
#    (потрібні, якщо для вашої версії Python немає готових збірок pyiceberg/pyroaring)
sudo apt install python3-venv build-essential python3-dev

# 2. Перехід до директорії бекенду (з кореня репозиторію)
cd backend

# 3. Створення віртуального оточення
python3 -m venv venv

# 4. Активація оточення
source venv/bin/activate

# 5. Встановлення залежностей
pip install -r requirements.txt

# 6. Запуск у режимі розробки (потрібен backend/.env, див. вище)
uvicorn main:app --reload --port 8000
```

Бекенд буде доступний за адресою **http://127.0.0.1:8000**, Swagger-документація — **http://127.0.0.1:8000/docs**.

**Тести бекенду** (Supabase підміняється in-memory базою, ключі, `.env` та інтернет не потрібні).
Команди виконуються **всередині віртуального оточення** з кроків 1–4 вище — у терміналі на початку рядка має бути `(venv)`:
```bash
cd backend                              # з кореня репозиторію
source venv/bin/activate                # якщо оточення ще не активоване
pip install -r requirements-dev.txt     # один раз: залежності + pytest
pytest -q                               # усі тести; у кінці рядок на кшталт «165 passed»
```
Корисні варіанти: `pytest -v` (кожен тест окремим рядком), `pytest tests/test_statuses.py` (один файл),
`pytest -k leaderboard` (тести, у назві яких є слово). Якщо тест впав, pytest покаже `FAILED`,
рядок із перевіркою та очікуване/отримане значення. Наступного разу достатньо `cd backend`,
`source venv/bin/activate` і `pytest -q` — перевстановлювати нічого не треба.

Ті самі тести автоматично запускаються на GitHub (вкладка **Actions**, файл `.github/workflows/tests.yml`) на кожен
push у `main` і на кожен pull request: у PR видно зелену галочку або червоний хрестик. Запускаються тести бекенду
(Python 3.12 і 3.13) та симуляції з `research/`.

> **Примітка:** Бекенд також задеплоєний на [Render](https://render.com). Якщо локальний бекенд не потрібен, у `frontend/.env.local` вкажіть актуальний URL з Render як `NEXT_PUBLIC_API_URL`. Безкоштовний інстанс Render «засинає» після періоду бездіяльності, тому перший запит може тривати до хвилини.

Swagger-документація на Render: **https://site-turing-crutchmasters-team-s.onrender.com/docs**

**Типові помилки під час встановлення (Ubuntu/Debian)**

| Повідомлення | Причина і що робити |
|---|---|
| `Command 'pip' not found` | Команду `pip` запускали поза оточенням. Створіть і активуйте `venv` (кроки 1–4): у ньому `pip` є. Системний `pip` ставити не потрібно |
| `error: externally-managed-environment` | Ubuntu забороняє `pip install` у системний Python. Рішення — `venv`: `python3 -m venv venv && source venv/bin/activate`, потім `pip install …`. Прапорець `--break-system-packages` не використовуйте |
| `The virtual environment was not created successfully` / `ensurepip is not available` | Не встановлено `python3-venv`: `sudo apt install python3-venv` |
| `No such file or directory: 'x86_64-linux-gnu-gcc'` | Не встановлено компілятор: `sudo apt install build-essential python3-dev` і повторіть `pip install`. Альтернатива — оточення на Python 3.12/3.13 (`python3.13 -m venv venv`), тоді компіляція не потрібна |
| `pytest: command not found` | Оточення не активоване або не встановлено `requirements-dev.txt`: `source venv/bin/activate && pip install -r requirements-dev.txt` |
| `ModuleNotFoundError: No module named 'fastapi'` (чи інший пакет) | Те саме: активуйте `venv` і виконайте `pip install -r requirements-dev.txt`. Перевірити, що використовується саме оточення: `which python` має вказувати на `…/backend/venv/bin/python` |
| `sudo apt install python3-xyz` → `Unable to locate package` | `xyz` у підказці pip — лише приклад. Ставити окремий пакет не потрібно, використовуйте `venv` |

> `(venv)` на початку рядка термінала зникає, коли ви відкриваєте нове вікно — тоді знову виконайте `source venv/bin/activate`.

## API

Основні групи ендпоінтів:

| Група | Опис |
|---|---|
| `/api/register`, `/api/login` | Реєстрація та авторизація |
| `/api/users/*` | Профіль, пошук, налаштування |
| `/api/teams/*` | Команди, запрошення, кік |
| `/api/tournaments/*` | Турніри, банер, лідерборд |
| `/api/rounds/*` | Раунди, сабміти, оцінювання, розподіл |
| `/api/invitations/*` | Запрошення учасників |
| `/api/jury-invitations/*` | Запрошення та управління жюрі |
| `/api/notifications/*` | Сповіщення |
| `/api/upload/*` | Завантаження файлів |

## База даних

Схема зберігається у директорії `database/`. Основні таблиці:

- `accounts` — користувачі та їх ролі

- `tournaments` — турніри
- `rounds` — раунди турніру

- `team_invitations` — запрошення до команд
